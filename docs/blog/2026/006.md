# 纯 C 手搓网络线程池,峰值 39 万 req/s

`net_threadpool` 是纯 C + 纯 POSIX(pthread + Berkeley Socket)实现的网络线程池服务器,外加一套多线程基准测试工具。没有第三方依赖,`gcc` 一条命令就能编译。

写完不只是跑通,还认真跑了一组「池线程数 × 客户端并发」的 benchmark 矩阵(每客户端 5000 请求,预热 10)。

## 架构

```
┌──────────────┐
│ 主线程        │  只做 accept()，把连接封装成任务
│ (acceptor)   │
└──────┬───────┘
       │ tp_submit()（队列满时阻塞 = 背压）
┌──────▼───────┐
│ 有界环形队列  │  由 pthread_mutex_t 保护
└──────┬───────┘
    cond_signal(not_empty)
┌──────┼──────┬─────────────┐
▼      ▼      ▼             ▼
worker worker worker      worker
```

主线程 accept + 有界任务队列 + N 个工作线程。线程数有上界,不会 1 连接 1 线程地无限创建。

## 条件变量谓词循环

同步的核心是「条件变量 + 谓词循环」的标准写法,天然免疫虚假唤醒:

```c
/* 谓词循环：队列空且未关闭则等待（自动处理虚假唤醒） */
while (tp->count == 0 && !tp->shutdown)
    pthread_cond_wait(&tp->not_empty, &tp->mtx);

/* 关闭且队列已排空：退出 */
if (tp->shutdown && tp->count == 0) {
    pthread_mutex_unlock(&tp->mtx);
    break;
}
```

用 `while` 而不是 `if`:条件变量可能被虚假唤醒,唤醒后要重新检查谓词,不满足就继续等。提交端同理,只是谓词换成「队列满」:

```c
int tp_submit(threadpool_t *tp, void (*fn)(void *arg), void *arg)
{
    pthread_mutex_lock(&tp->mtx);

    /* 谓词循环：队列满且未关闭则等待（背压：限制未处理连接数） */
    while (tp->count == tp->cap && !tp->shutdown)
        pthread_cond_wait(&tp->not_full, &tp->mtx);

    if (tp->shutdown) { pthread_mutex_unlock(&tp->mtx); return -1; }

    tp->queue[tp->tail] = (tp_task_t){ fn, arg };
    tp->tail = (tp->tail + 1) % tp->cap;
    tp->count++;

    pthread_cond_signal(&tp->not_empty);
    pthread_mutex_unlock(&tp->mtx);
    return 0;
}
```

队列满时 `tp_submit()` 阻塞 → accept 线程自然停住 → 内核 backlog 兜底,形成一条限流链条,不会无限堆积连接。另外任务是在**锁外执行**的——唤醒别人之后先释放锁再 `t.fn(t.arg)`,避免长时间持锁把提交者全堵住。

## 56 组 benchmark

峰值吞吐(req/s):

| 池线程数 \ 并发 | 1 | 8 | 32 | 128 |
|---|---|---|---|---|
| 1  | 66k | 63k | 60k | 64k |
| 2  | 66k | 123k | 118k | 119k |
| 4  | 62k | 202k | 194k | 197k |
| 8  | 61k | 270k | 280k | 270k |
| 16 | 66k | 274k | 378k | **391k** |
| 32 | 66k | 262k | 358k | 375k |

几点结论:

- **单连接基线** ~62–66k req/s,p50 ≈ 13.6µs——基本是本机回环网络的往返延迟下限,也是所有数据的参照系
- **近似线性扩展**:1→2→4→8 线程,66k→123k→202k→270k,扩展比接近 1
- **饱和点**:测试机 12 核,池 = 16、并发 128 时达峰值 ~39 万 req/s
- **过订阅**:池 ≥ 32 吞吐不再上升;并发 ≥ 32 时平均延迟从 ~37µs 恶化到 73–148µs——线程过订阅的上下文切换是经典模型的瓶颈

正确性验证也做了:池 = 1、队列容量 = 4、64 客户端同时压入 12.8 万请求,全部完成、零错误、无死锁。

## 优雅关闭

`tp_destroy()`:置 `shutdown` → `broadcast` 唤醒所有等待线程 → worker 排空队列后自行退出 → 主线程 `pthread_join` 回收:

```c
pthread_mutex_lock(&tp->mtx);
tp->shutdown = 1;
pthread_cond_broadcast(&tp->not_empty);  /* 唤醒所有等待的工作线程 */
pthread_cond_broadcast(&tp->not_full);   /* 唤醒被阻塞的提交者 */
pthread_mutex_unlock(&tp->mtx);

for (size_t i = 0; i < tp->nthreads; i++)
    pthread_join(tp->threads[i], NULL);
```

广播而不是单发,因为可能有多个线程同时在等,要把**所有**等待线程都叫起来。
