# 从阻塞 socket 到 select/poll/epoll:I/O 多路复用

接上一篇的阻塞式 socket(008),这周把 I/O 多路复用的三种方式都手写了一遍——`select`、`poll`、`epoll`,最后还用非阻塞客户端做了压测。

## 为什么需要多路复用

阻塞 `recv` 一次只能盯住一个连接;1 连接 1 线程在连接数上来之后不现实。多路复用的思路是一个线程同时盯住大量 fd,有事件了再处理。`socket_test/` 里三个版本刚好是这条演进的完整轨迹。

## select

`tcp_select_server_v1.c`。核心是三套 `fd_set` 位图(`FD_SET` / `FD_ZERO` / `FD_ISSET`):

```c
fd_set readfds, writefds, master_read, master_write;
...
int ready = select(max_fds+1,&readfds,&writefds,NULL,NULL);
// 然后线性遍历 0..max_fds，看每个 fd 是否 FD_ISSET
```

每次调用都要把集合拷给内核,返回后还得从头遍历所有 fd;因为 `select` 会原地改写集合,所以每轮要用 `master_*` 重建。fd 上限受 `FD_SETSIZE`(glibc 默认 1024)限制,所以这个版本 `MAX_CONNECTIONS` 只敢定 10。复杂度 O(连接数)。

```c
readfds = master_read;
writefds = master_write;
```

## poll

`tcp_poll_server_v1.c`。把位图换成 `struct pollfd` 数组,没有 1024 的上限,事件用 `POLLIN` / `POLLOUT` / `POLLHUP` 表达。但同样每次都要把整个数组传给内核、遍历所有 fd:

```c
struct pollfd fds[MAX_CONNECTIONS + 1];
...
int ret = poll(fds,active_conns,-1);
```

断开连接时用「把最后一个挪过来覆盖」的方式压缩数组,避免空洞让遍历范围越来越大:

```c
int remove_conn(int i,struct pollfd fds[],Client c[],int active_conns){
    if(i < 0 || i > active_conns){
        return -1;
    }
    close(fds[i].fd);
    if(i != active_conns - 1){
        fds[i] = fds[active_conns - 1];
        c[i - 1] = c[active_conns - 2];
    }
    ...
    return active_conns - 1;
}
```

这一步开始,服务器和客户端 fd 都设成非阻塞(`fcntl(fd, F_SETFL, O_NONBLOCK)`),`recv` / `send` 遇到 `EAGAIN` / `EWOULDBLOCK` 就下次再试——不能像阻塞版那样直接在系统调用里等。

## epoll

`tcp_epoll_server_v2.c` 是这轮的最终形态。epoll 把维护工作交给内核:只用 `epoll_ctl` 注册一次,内核维护就绪链表,`epoll_wait` 只返回真正就绪的 fd,复杂度 O(就绪连接数)而不是 O(总连接数)。

每个连接用 `epoll_event.data.ptr` 挂一个 `Client` 结构(收发缓冲、偏移、是否关闭):

```c
typedef struct Client{
    int client_fd;
    char recv_buf[1024];     // 接收临时区
    char recv_message[4096];
    size_t used;             // 还没被解析出去的字节数
    char send_buf[4096];     // 待发送数据
    size_t send_len;
    size_t send_offset;
    bool should_close;
}Client;
```

事件循环按就绪事件分发:

```c
while(1){
    int n = epoll_wait(epfd,evs,MAX_EVENTS + 1,-1);
    for(int i = 0;i < n;i++ ){
        uint32_t revents = evs[i].events;
        if(evs[i].data.ptr == NULL && (revents & EPOLLIN)){   // 监听 socket
            int cli_fd = accept(server_fd,NULL,NULL);
            ...
            epoll_ctl(epfd,EPOLL_CTL_ADD,cli_fd,&evc);
            continue;
        }
        Client *c = evs[i].data.ptr;
        if(revents & EPOLLIN){
            handle_recv(epfd,&evs[i]);   // 按 '\n' 拆成一行一行
        }
        if(revents & EPOLLOUT){
            handle_send(epfd,&evs[i]);   // 有数据待发时注册 EPOLLOUT
        }
        ...
    }
}
```

这里几个细节:

- **按需注册 `EPOLLOUT`**:数据没发完时才把事件改成 `EPOLLIN | EPOLLOUT`,发完再只留 `EPOLLIN`。如果一直挂着 EPOLLOUT,没数据时也会反复触发,等于忙转
- **`recv` 攒到 `'\n'` 才算一行**:TCP 是字节流,一次 `recv` 不一定是一整条消息,缓冲区里攒着按行切分
- **`MSG_NOSIGNAL`**:对端断开时 `send` 会触发 `SIGPIPE` 把进程带走,加上这个标志避免
- **`EPOLLRDHUP`**:提前感知对端关闭
- 规模也放开了:`MAX_CONNECTIONS` 16384、`MAX_EVENTS` 8192、`LISTEN_BACKLOG` 8192,对比 select 版的 10,该换就换

还有两处注释写着「尚未实现」:连接数超上限时的**背压**(目前是直接 close 掉),以及**超长消息**的处理(目前是报错断开而不是回退)。这两个尾巴留着下一步补。

## 压测客户端

`stress_test_client.c` 是个非阻塞的多客户端压测工具:用 `poll` 同时管理几百个连接(默认 256 个客户端),每个连接发多条请求,并且**校验回显的完整性**——发完 `send_buf` 后,`recv` 的数据要按 `'\n'` 找边界、和发出内容 `memcmp` 完全对上才算一次请求完成,同时记录每请求延迟、算 QPS。Ctrl-C 能优雅退出并打印汇总。

```c
// 每个 client 是个小状态机
CLIENT_CONNECTING → CLIENT_WRITING → CLIENT_READING → CLIENT_DONE / CLIENT_FAILED
```

自己写压测工具的好处是能验证正确性、拿到延迟分布,不用再单开一堆命令行进程手数 QPS。

## 收获和没做完的

- select/poll/epoll 是**演进不是替代**:连接少时前两者足够,连接多、大部分空闲时 epoll 的优势才明显
- 非阻塞 + 事件循环的复杂度确实比阻塞高不少——每个连接都是个小状态机,数据收发、缓存的每一环都要自己兜
- 还没做:accept 背压、超长消息降级、多线程 + epoll、事件驱动上的 HTTP 解析。对照 006 的经典线程池模型,这两条路线各有各的坑,后面慢慢填
