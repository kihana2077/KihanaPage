# 线程进阶:从竞争到同步,再到手写线程池

这一批练习从线程创建一路推到互斥锁、条件变量、信号量、读写锁,最后手写了一个线程池。

## 从竞争到同步

`pthread_no_mutex.c` 和 `pthread_have_mutex.c` 是两组对比实验:前者不加锁,多个线程并发修改共享变量;后者加互斥锁保护。跑一遍就会看到「数据错乱」——后写覆盖先写,结果不可预测。并发编程第一课:共享数据必须同步。

## 生产者消费者

`prod_cons_prob.c` 是最小的生产者消费者模型。开头的注释直接点明了动机:

```c
//旨在构建一个最小的生产者消费者模型，以便理解服务器接收请求之后的任务分发策略
```

这是带着「服务器怎么分发任务」的工程视角在学,直接通向后面的线程池。

```c
pthread_mutex_t mutex = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t not_empty  = PTHREAD_COND_INITIALIZER;
pthread_cond_t not_full   = PTHREAD_COND_INITIALIZER;

void *producer(void *arg){
    for(int i = 0;i<10;i++){
        pthread_mutex_lock(&mutex);
        while(ready == 1){              // 槽满就等
            pthread_cond_wait(&not_full,&mutex);
        }
        data = i+1;
        ready = 1;
        pthread_cond_signal(&not_empty); // 通知消费者
        pthread_mutex_unlock(&mutex);
        printf("Producer:: %d\n",data);
    }
    return NULL;
}

void *consumer(void *arg){
    for(int i = 0;i<10;i++){
        pthread_mutex_lock(&mutex);
        while(ready == 0){              // 槽空就等
            pthread_cond_wait(&not_empty,&mutex);
        }
        ready = 0;
        pthread_cond_signal(&not_full);  // 通知生产者
        pthread_mutex_unlock(&mutex);
        printf("Consumer:: %d\n",data);
    }
    return NULL;
}
```

两个条件变量 `not_empty` / `not_full` 分开用——生产者等「空位」、消费者等「有货」,各等各的。`while` 重查谓词,躲开虚假唤醒。

## 信号量版

`sem_pro_con_prob.c` 用信号量重写,缓冲区升级成环形数组(`BUF_SIZE=10`),`full` / `empty` 两个信号量做「还有多少库存 / 还有多少空位」的计数:

```c
sem_wait(&empty);   // 申请一个空位，没有就阻塞
produce(i,buf);
sem_post(&full);    // 产出 +1

sem_wait(&full);    // 申请一个已产出，没有就阻塞
consume(i,buf);
sem_post(&empty);   // 空位 +1
```

信号量的好处是自带计数——`empty` 初始化为 `BUF_SIZE`,`full` 初始化为 0,天然就是「容量」和「库存」。

## 读写锁

`wr_rd_lock.c`:读写锁读可共享、写独占,是「读多写少」场景的优化:

```c
pthread_rwlock_rdlock(&rwlock);     // 读锁：可共享
pthread_rwlock_wrlock(&rwlock);     // 写锁：独占
```

3 个 Reader 共享一个配置变量,1 个 Writer 每次 +10。读不互斥、写才互斥,吞吐比一刀切的互斥锁高。

## 手写线程池

然后把手头的知识串起来,手写 `thread_pool.c`。注释写着「从模拟面向对象到结构体撰写构造函数」——用 C 写出一点 OOP 的味道。线程池 = 一个有界任务队列 + N 个等待的工作线程:

```c
#define MAX_TASK 100

typedef struct Task
{
    void (*function)(void *);   // 函数指针 = 任务本体
    void *arg;
}Task;

typedef struct TaskQueue{
    Task queue[MAX_TASK];
    int front;
    int rear;
    int size;
    pthread_mutex_t mutex;
    pthread_cond_t cond;
    int shutdown;
}Queue;
```

```c
int push(Queue *q,Task task){
    pthread_mutex_lock(&q->mutex);
    if(q->size == MAX_TASK){            // 队列满
        pthread_mutex_unlock(&q->mutex);
        return -1;
    }
    q->queue[q->rear] = task;
    q->rear = (q->rear + 1) % MAX_TASK; // 环形缓冲
    q->size++;
    pthread_cond_signal(&q->cond);      // 唤醒一个 worker
    pthread_mutex_unlock(&q->mutex);
    return 0;
}

Task pop(Queue *q){
    Task task;
    pthread_mutex_lock(&q->mutex);
    while(q->size == 0){                // 队列空就等
        pthread_cond_wait(&q->cond,&q->mutex);
    }
    task = q->queue[q->front];
    q->front = (q->front +1)% MAX_TASK;
    q->size--;
    pthread_mutex_unlock(&q->mutex);
    return task;
}
```

worker 里就是死循环 `pop → 执行 → 再来`。任务只要「函数指针 + 参数」就能提交,线程池本身跟业务无关。

## 与 net_threadpool 的关系

这个 `thread_pool.c` 其实是 8 月 13 日 `net_threadpool`(006,峰值 39 万 req/s)的前身:

- `thread_pool.c`:学习版,`MAX_TASK=100`、3 个 worker、还带着 `sleep(10)` 这种教学痕迹
- `net_threadpool`:生产版,有界环形队列 + 双条件变量 + 背压 + 优雅关闭 + 56 组 benchmark

从「能跑」到「跑出 39 万 req/s」,中间大概隔了一个星期。
